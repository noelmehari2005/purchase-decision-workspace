## Preparation and evidence

Use a separate owner-controlled disposable email/password account, never the owner's main identity. The owner enters passwords and completes account registration, verification links and reset submissions privately. Do not record passwords, reset links, session/provider tokens or full provider responses in this document. A separate browser tab was opened through the hosted app's Create account flow; the main workspace tab was not edited or signed out. Creating a second Auth0 identity does not itself grant application access: Render's approved tester list and verified email are both required.

Targeted regression on November 18: `backend.tests.test_auth`, `test_auth_provider`, `test_spa_auth`, `test_email_check` and `test_lifecycle` discovered 70 tests: 64 passed, six MongoDB integration tests skipped because no test database was supplied. Tests use controlled providers and synthetic identities; no mail or provider user deletion was performed. They cover neutral reset responses and rate limits, reset revocation including same-second timestamps, one-hour idle/24-hour absolute boundaries, profile/allowlist failures, signed-token checks, verified SMTP TLS and lifecycle recovery rules. This is not a substitute for hosted inbox receipt or browser verification.

## Live sequence

1. Create only the disposable account through the hosted app; note whether Auth0's verification message actually arrives (including spam). Before clicking its verification link, check that private storage is unavailable. The generic staging denial alone does not distinguish an unverified email from an address outside the tester list; use the controlled test matrix and redacted server diagnostics when needed.
2. Add only that specific address to Render's comma-separated `PDW_TESTER_EMAILS`, preserving the owner's existing address. The owner performs this access change and saves/redeploys. With the address approved but still unverified, retry sign-in and confirm no private session is issued. Complete verification privately, start a fresh sign-in, and confirm access then works.
3. Confirm the disposable account starts with no access to the main account's saved workspaces. Save a fictional workspace under a clear test title. Refresh/reopen, sign out/refresh, then sign back in. Record the results without copying personal workspace contents.
4. Keep the disposable session open in the app. Request a reset for the same account from a separate signed-out tab using Forgot your password. Check the neutral response and actual inbox delivery. The owner changes the password privately. On the existing app tab's next session check (normally within 20 seconds), private access must close and stay closed after refresh. Fresh sign-in with the new password must reopen the disposable workspace. Never reset the main account as a shortcut.
5. Verify one-hour idle expiry without interacting with the disposable app tab, leaving the normal server configuration unchanged; automatic session polling must not count as activity. Compare with the controlled-clock boundary tests rather than shortening a real account's deadline. The 24-hour absolute boundary is covered by controlled clocks; mark a separate real-time observation pending unless actually performed. Do not claim a full-day hosted test from an automated unit test.

## Separate email systems and known constraints

Auth0 verification/password-reset mail and the Python backend's deletion notices are separate delivery paths. Receiving one does not establish the other works. Hosted backend SMTP and notification processing still need verification. The configured development/test sender was previously restricted to its provider account email; do not assume delivery to a different disposable address or Gmail alias without verifying authorized recipient/sender coverage. Do not open or modify that provider account without the owner's permission. No paid plan/domain is authorized.

Deletion/recovery testing is a later explicitly scoped step for the disposable account only. Do not run broad maintenance as an SMTP probe, shorten recovery windows, purge live data or delete Auth0 users merely to check email. Queued email is not proof of SMTP acceptance; acceptance is not proof of inbox delivery. Scheduling, backups, deletion-ledger replay and restore/expiry operations remain outstanding.

Auth0 documents that verification links are emailed on signup by default ([verification flow](https://auth0.com/docs/manage-users/user-accounts/verify-emails)). The built-in provider is intended for testing and has delivery/reliability restrictions ([provider guidance](https://support.auth0.com/center/s/article/Emails-to-Gmail-from-Auth0-never-arrive)). Those limitations are not proof of the cause of the missing first message.
